
\chapter{Pipeline Implementation}
\label{chap:implementation}

This chapter explains how the architecture from Chapter~\ref{chap:architecture} and the data--model contract from Chapter~\ref{chap:data_model} are realized in the repository implementation. The aim is not to provide a code listing, but to make the implementation auditable. Every architectural rule from Chapter~\ref{chap:architecture} and every contract element from Chapter~\ref{chap:data_model} maps to a specific Python module, configuration source, runtime package, or run-scoped artifact in the repository.

\section{Repository Layout and Execution Entry Point}
\label{sec:repository_layout}

The repository separates source code, configuration, runtime contract packages, execution utilities, and run-scoped evidence into distinct areas. This separation supports the offline-first claim: the pipeline can be inspected and executed from local files without relying on a managed cloud platform. Runtime model packages are kept together with their companion artifacts (the scaler, label order, monitoring baseline, contract metadata, and evaluation evidence), so that each promoted runtime contract is a self-contained, inspectable unit. Preprocessing and monitoring thresholds are externalized as configuration rather than hidden inside notebooks, which makes them part of the reproducibility boundary.

The main scripted execution path is concentrated in a single entry point that assembles the layered configuration, resolves the active runtime contract, and invokes the stage-oriented pipeline. Concentrating execution this way keeps the thesis evidence reproducible from one command, rather than dependent on disconnected notebooks or ad-hoc scripts. A runbook of all reproducibility commands is provided in Appendix~\ref{app:commands}.

\section{Technology and Design Rationale}
\label{sec:technology_rationale}

The implementation choices in this chapter are deliberate rather than incidental; the main choices below each map to an offline-first, contract-driven goal defined in Chapters~\ref{chap:architecture} and~\ref{chap:data_model}. This section states the main technology and design decisions together with their rationale, so that the implementation reads as a set of engineering choices rather than as defaults; the broader problem of selecting an open-source MLOps tool stack is itself an active research topic~\cite{ruf2021demystifying,hewage2022mlops}. A detailed tool and version reference is collected in the technology-stack appendix.

Tools are selected for reproducibility and contract safety in an offline-first setting, not for production-scale serving or orchestration, which are outside the defended scope.

\section{Configuration Layering}
\label{sec:configuration_layering}

The pipeline uses layered configuration rather than hard-coded stage behavior. This is necessary because the same codebase is used for labeled evaluation, deployment-style inference, monitoring, API execution, and controlled diagnostic runs. The configuration layer defines which model package is active, which scaler and baseline are used, which preprocessing path is applied, and which stages are enabled.

This layering supports reproducibility and controlled variation. A normal thesis run uses the proposed model's default runtime contract and the standard preprocessing settings defined in the layered configuration. A diagnostic run can then change a specific flag, such as a preprocessing option or an alternative model path, without editing the underlying implementation. This keeps experimental variation explicit and reviewable.

Configuration changes must not silently break the runtime contract. A changed model path must remain compatible with the corresponding scaler, label order, and monitoring baseline. A changed preprocessing flag must be interpreted as a new runtime condition unless the model and baseline were prepared under the same assumption. For this reason, configuration assembly is part of the system's contract-enforcement mechanism.

\section{Runtime Contract Implementation and Artifact Loading}
\label{sec:contract_loading}

The runtime contract defined in Chapter~\ref{chap:data_model} is realized in code through three coordinated mechanisms: a single source of path defaults, a scaler-loading utility that validates artifact provenance, and a configuration-build step that binds the model artifact to its accompanying scaler and monitoring baseline. The implementation goal is not only to load files, but to ensure that the model receives input prepared under the same assumptions that defined its training and fine-tuning.

The path defaults are concentrated in a single configuration module that references the active runtime contract directory of the proposed model. That directory holds all artifacts that must be interpreted together: the model checkpoint, the train-only scaler, the label-order file, the monitoring baseline, the contract metadata, the integrity record, and the evaluation evidence. Earlier runtime candidates are retained through separate constants so that rollback or diagnostic comparison remains possible without restructuring the configuration layer.

Before the inference path consumes the scaler, a provenance check confirms that it declares train-only origin and carries the expected six-channel layout. This guards against the case where a syntactically valid but contractually incompatible scaler is loaded into the inference path. The scaler is loaded from the promoted runtime contract and is never fitted on User~7 or deployment-style sessions; this preserves the train--serve feature space defined during Garmin users~1--6 training.

The API layer consumes the runtime contract through the same default constants as the batch path, all of which can be overridden by environment variables when needed. Environment overrides allow ad-hoc rollback or side-by-side comparison, while the unmodified defaults keep the pipeline aligned with the defended contract.

\subsection{Same-Folder Invariant Enforcement}
\label{sec:contract_invariant}

Chapter~\ref{chap:architecture} introduced the same-folder invariant as an architectural rule: the model, scaler, label order, and monitoring baseline must live in one runtime contract folder and must be promoted together. The implementation of this rule is centralized in the configuration-assembly step, which is invoked at configuration-build time, before preprocessing or inference starts.

The helper resolves the runtime contract folder from the active model path and compares it against the configured scaler path. The three resulting outcomes correspond to the rules stated in Chapter~\ref{chap:architecture}, Table~\ref{tab:runtime_contract_rules}.

If the configured scaler already lives in the active model folder, the configuration is accepted unchanged and the runtime contract is treated as coherent. If the scaler path points outside the active model folder but a compatible scaler exists inside the active folder, the helper corrects the stale path and records a warning. If no compatible same-folder scaler exists, the helper fails fast before inference begins.

The monitoring baseline is aligned through the API and pipeline configuration defaults, which both resolve to the active contract folder, and is validated by the pytest contract tests. The invariant is enforced before any preprocessing or inference artifact is written. A misconfigured run therefore either proceeds under the coherent contract that the operator likely intended, or fails before producing misleading outputs. This implementation does not solve every possible form of contract drift, but it removes a high-risk failure mode: loading a model from one runtime package while scaling inputs with an artifact from another package.

\section{Stage Execution and Artifact Trail}
\label{sec:stage_oriented_pipeline}

The pipeline is implemented as a sequence of stage-oriented components. Each stage has a bounded responsibility and writes outputs that can be inspected after execution. The assessment path can therefore be written as the composition
\[
R = S_7\!\left(S_6\!\left(S_5\!\left(S_4\!\left(S_3\!\left(S_2\!\left(S_1(x)\right)\right)\right)\right)\right)\right),
\]
where $x$ is the input session and $R$ is the run result, including the governance decision. On unlabeled runs $S_5$ acts as the identity, since evaluation metrics require labels; the composition is otherwise unconditional. This composition mirrors the architectural separation introduced in Chapter~\ref{chap:architecture}: Stages~1--7 form the operational assessment path, while Stages~8--10 belong to the governed mutation path and are not part of this default composition.

To make the mapping concrete, it is useful to trace a single execution. When the pipeline entry point is invoked on a recorded session, it first assembles the layered configuration and resolves the active runtime contract of the proposed model. Stage~1 ingests the session and standardizes column access; Stage~2 validates schema, units, and timestamps; Stage~3 converts units where required, applies the saved train-only scaler, and constructs the row-wise windows of shape $(200,6)$; Stage~4 runs inference and records per-class probabilities; Stage~5 computes evaluation metrics when labels are present; Stage~6 derives the confidence, temporal, drift, and dominant-class signals; and Stage~7 combines them into a single governance decision. On the labeled User~7 external session, for example, this path produced 989 windows and routed the run to \texttt{REVIEW} with \texttt{auto\_retrain=false}, writing the full evidence chain shown in Figure~\ref{fig:run_scoped_artifact_trail}. No mutation stage is entered unless review, labels, and validation evidence justify it.

\subsection{Run-Scoped Artifact Trail}

Each pipeline execution writes run-scoped artifacts so that the path from input data to trigger decision can be reconstructed after the run. This is the implementation side of the lineage principle discussed in Chapter~\ref{chap:architecture}. The pipeline does not rely only on console output; it writes structured files that preserve validation, transformation, inference, monitoring, and trigger evidence.

Run outputs are stored under an \texttt{artifacts/<run\_id>/} convention and are also summarized in pipeline logs. A run identifier connects the input session, intermediate artifacts, and final decision, as illustrated in Figure~\ref{fig:run_scoped_artifact_trail}. \section{Interfaces, Reproducibility, and Maturity}
\label{sec:api_execution_interfaces}

The repository supports both scripted execution and API-based inference. Scripted execution is used for reproducible thesis runs because it makes input paths, configuration values, and output folders explicit. The API interface provides a serving-style entry point for submitting wearable sensor files and receiving predictions or monitoring outputs.

The API does not redefine the runtime contract. It uses the same model path, scaler path, label order, baseline, and configuration defaults as the batch pipeline. This prevents the API from becoming a parallel inference path with different preprocessing assumptions. When environment variables are used to override paths, they are treated as explicit runtime changes rather than hidden defaults.

The serving interface is a browser-based dashboard. The upload screen presents three modes
and a stage strip that makes the pipeline boundary visible before any file is submitted.
The strip shows which stages run automatically on the server (Stages~1--3: ingestion,
validation, and transformation), which stages produce the visible results (Stages~4--7:
inference, evaluation, monitoring, and trigger decision), and which stages are review-gated
and require a human action before they execute (Stages~8--10). The three upload modes
differ in how the raw recording is supplied. The first mode accepts two separate CSV files,
one containing the accelerometer channels and one the gyroscope channels; the preprocessing
pipeline fuses them using the same channel-alignment logic as the batch path. The second
mode accepts a single pre-fused activity CSV without a label column, which the dashboard
routes as an unlabeled deployment-style session and processes using only the proxy monitoring
signals. The third mode accepts the same pre-fused format with an additional ground-truth
label column, enabling a labeled evaluation session where accuracy and quality metrics are
also computed.

After upload, the results are returned in three panels. The monitoring panel reports the
three-layer signal summary: session mean confidence with its uncertain-window percentage,
temporal transition rate shown as both a raw session value and a smoothed per-window trace,
and per-channel distribution drift score, each with a color-coded severity status. The
governance panel reports the trigger decision, the retraining status, and, when applicable,
the reason for escalation or cooldown suppression. The prediction panel lists each window's
predicted activity class and confidence score. When the upload carries ground-truth labels,
the dashboard additionally shows an evaluation card with session-level accuracy,
macro-averaged F1, and their temporally smoothed variants, together with a per-class
confusion matrix. Appendix~\ref{app:walkthrough} provides annotated screenshots of both a
labeled and an unlabeled session walking through each panel in turn.

The API and batch paths are treated as contract-equivalent execution interfaces: both resolve the same promoted runtime package, apply the same scaler and label order, and must therefore remain behaviorally aligned. This alignment is verified as an implementation test rather than asserted as a separate model-performance claim; the contract and upload-mode tests check that both paths consume the identical runtime contract so that the API cannot silently diverge into a different preprocessing path.

Verification and portability are supported by the test suite and the promoted package rather than by ad-hoc scripts. Automated contract tests verify that the active proposed-model package loads correctly, that the model, scaler, baseline, and label order stay aligned, and that the API and batch upload modes behave consistently. In the defended runtime, both the batch pipeline and the FastAPI serving path load the native \texttt{.keras} model from the promoted contract folder; the SavedModel-compatible export is kept alongside it for cross-environment portability, not as a separate serving path.

\subsection{Experiment Tracking Across the Two Execution Paths}
\label{sec:experiment_tracking}

Both execution interfaces record evidence to MLflow as two separate experiments, mirroring the contract-equivalent but operationally distinct relationship described above. The batch path logs to the \texttt{har-production-pipeline} experiment, where each stage contributes its own metrics so that an entire governed run, from ingestion through the trigger decision, is reconstructable from the tracking record. The serving path logs to the \texttt{inference-production} experiment, capturing the focused inference-and-monitoring evidence of a single upload. Keeping the experiments separate prevents interactive serving runs from diluting the batch-run history while still recording both under one local tracking store.

Each run logs a curated set of essential signals rather than raw telemetry. For the batch pipeline this is one or two metrics per stage: the input shape, the validation-gate result, the window count, inference timing and mean confidence, the temporal, drift, and dominant-class monitoring signals, and the final retraining decision with its alert level. Redundant confidence statistics and constant configuration flags, which either repeat across stages or never vary between runs, are deliberately excluded so the tracking record stays auditable rather than noisy. The serving path logs the analogous proxy set: confidence, drift, the raw and smoothed transition rate, per-activity counts, and, only when the upload carries ground-truth labels, accuracy and macro-F1. MLflow therefore records what the pipeline observed on a specific run, making it possible to compare monitoring severity or trigger outcomes across sessions without rerunning the pipeline~\cite{zaharia2018mlflow}. Representative screenshots of the dashboard and of both MLflow experiments are collected in Appendix~\ref{app:walkthrough}.

\subsection{Reproducibility and Environment Control}
\label{sec:reproducibility_environment}

The implementation is designed for local reproducibility, following reproducibility practice for scientific machine learning~\cite{gardner2018enabling,bahaidarah2021reusable,munappy2019data}. Configuration files, runtime contract folders, run-scoped artifacts, and tests are kept inside the repository structure so that a run can be reproduced or inspected without a managed production platform. Docker and dependency files support environment consistency, while local execution keeps the defended runtime aligned with the offline-first scope.

A specific reproducibility issue concerns model format portability across environments. Training and conversion may occur in an environment using older TensorFlow/Keras conventions, while thesis execution may occur in a newer environment. To reduce this compatibility risk, the runtime contract retains the native \texttt{.keras} artifact used by the defended batch and API paths together with a SavedModel-compatible export for portability, while additional legacy or environment-specific artifacts may be kept as supporting material. This decision belongs to implementation reproducibility: the model package must be loadable by the defended inference environment, not only by the training notebook.

Automated tests provide another reproducibility layer. The defended suite contains 88 tests across 11 files. Its largest families guard exactly the thesis-critical behavior: Stage~6 monitoring (16 tests), Stage~7 trigger policy (14), end-to-end pipeline execution (12), API upload modes (10), and runtime-contract consistency (5). The remaining tests cover ingestion, schema validation, unit conversion, preprocessing, and component-level checks. Contract tests verify that configuration defaults, model paths, scaler paths, API defaults, and runtime assumptions remain aligned, and a continuous integration workflow runs the full suite on every push, so contract regressions surface before they reach the defended branch. These tests are not substitutes for model evaluation, but they reduce the risk that code changes silently break the runtime contract. In an offline-first thesis setting, such checks are valuable because reproducibility depends on local files staying consistent over time.

The roles of the two artifact-management tools are distinct. DVC \emph{is} part of the defended reproducibility mechanism: the raw, processed, and prepared data, the pretrained models, the promoted runtime-contract folder, and the defended evidence run are DVC-tracked, so they can be restored from content-addressed storage through Git-tracked pointer files~\cite{kuprieiev2023dvc}. MLflow records what the pipeline observed on a run; DVC or the release bundle supplies the artifacts the pipeline consumed. The proposed model's runtime package also includes an integrity manifest, so the model, scaler, baseline, and label-order files can be verified as one coherent package.

Containerization follows the same contract discipline. Two Docker images are defined: a training image with the full training stack and Stage~1--7 entry point, and a lean inference image that mounts the proposed model's contract folder as a read-only volume. This keeps the frozen assessment path separate from the mutation path described in Chapter~\ref{chap:architecture}. Data and models are not baked into either image; the deployment unit remains the runtime-contract folder, and Docker is used as a local reproducibility aid rather than as a Kubernetes-style production-serving claim.

\subsection{MLOps Maturity Position}
\label{sec:mlops_maturity_position}

The implementation places this thesis most closely at MLOps Level~1: pipeline automation with reproducible batch execution~\cite{kreuzberger2023mlops,hewage2022mlops}. It exceeds a manual notebook workflow because ingestion, validation, transformation, inference, monitoring, and trigger evaluation are staged, configuration-controlled, and artifact-producing. It remains below Level~2 because retraining, baseline update, deployment, and orchestration are governance-gated rather than automatic.

\section{Chapter Summary}

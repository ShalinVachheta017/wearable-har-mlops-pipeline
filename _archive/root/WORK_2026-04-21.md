## A. Executive Summary

**What the repo actually does today** (verified from source, not claims):

- An 11-stage offline MLOps pipeline orchestrated by `src/pipeline/production_pipeline.py` via `run_pipeline.py`. Stages 1–7 are the operational core (ingest → validate → transform → infer → evaluate → monitor → trigger). Stages 8–10 are the conditional retraining/registration/baseline-rebuild branch. Stage 11 is optional calibration/UQ.
- Stage 6 monitoring (`src/monitoring/post_inference_monitor.py`) implements 3 layers: confidence, temporal flip rate, and z-score drift vs a normalized baseline.
- Stage 7 trigger governance (`src/trigger_policy.py`) applies 2-of-3 voting, consecutive-warning escalation, 24h cooldown, and a collapse guard.
- AdaBN and TENT are **fully implemented** (`src/domain_adaptation/adabn.py` 163 LOC, `src/domain_adaptation/tent.py` 290 LOC) and wired through Stage 8 `ModelRetrainingConfig.adaptation_method ∈ {adabn, tent, adabn_tent, pseudo_label}`.
- There is **no OOD/energy-based module** in code. `src/ood_detection.py` does not exist. OOD is referenced in the thesis only as a concept (glossary + honest "we don't claim OOD detection" caveats).

**What the thesis can safely claim (evidence-backed)**:
- Offline-first, single-machine, governed HAR lifecycle with explicit stage boundaries.
- Three-layer monitoring feeding a 2-of-3 trigger policy with cooldown and collapse-pattern routing to `REVIEW`.
- Honest negative-result evidence (26-session baseline vs unit-fix+abstain, confidence unchanged at 0.8578, dominant-class share moved).
- AdaBN/TENT as *implemented optional adaptation methods*, not core contribution.

   - `warn <= dominant_pct < critical` → add to alerts but keep status at `HEALTHY` or upgrade to `WARNING`
   - write `results["dominant_class"]`, `results["dominant_pct"]`, `results["dominance_warning"]`, `results["dominance_critical"]`

3. **`src/components/post_inference_monitoring.py:60-67`** — pass the two new config values into the `PostInferenceMonitor(...)` constructor.

4. **`src/evaluate_predictions.py:225`** — replace hardcoded `dominant_pct > 95.0` with a constructor-injected value read from config, OR leave Stage 5 as-is (still 95% for the informational flag) and document that Stage 6 now owns the tiered check.

5. **`src/trigger_policy.py:355`** — replace `dominant_pct >= 95.0` with `self.thresholds.dominant_pct_critical` and add a `TriggerThresholds.dominant_pct_critical = 95.0` field. Keep cond_3 (90% + no transitions + high confidence) unchanged — it's a different signal.

**Expected effects**:

## A. Extra Safety Risks Not Covered in the Current Refactor Plan

1. **7 modules in `src/` mutate `sys.path`.** `src/cli.py:15`, `src/preprocess_data.py:29`, `src/evaluate_predictions.py:82`, `src/run_inference.py:71`, `src/train.py:59`, `src/trigger_policy.py:47`, `src/model_rollback.py:40`, and `src/monitoring/baseline_builder.py:84` all insert the project root at import time. Any file move during refactor silently changes resolution order. Refactor plan §L already locks these files, but the `sys.path` mutation pattern itself is not on the "do not touch first" list.
2. **Pipeline-to-component imports are all deferred (function-local).** 11 `from src.components.<stage> import …` calls are inside `_run_stage_N()` helpers in `src/pipeline/production_pipeline.py:226..502`. `src/pipeline/__init__.py` explicitly notes `# Keep old import available for backwards compat (deferred to avoid circular)`. Refactor-time import-path cleanup could accidentally move these to module top, triggering circular imports that only show up on cold import.
